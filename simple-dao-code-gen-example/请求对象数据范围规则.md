# 请求对象数据范围规则

本文说明代码生成的基础请求对象、租户请求对象、组织请求对象和个人请求对象如何共同限制数据范围。

该文档随 `gen-code` 输出到项目根目录和实体模块目录。

代码生成哈希校验码：[de2ffb22a14c97a3fc9b4b0445179220]，请不要修改和删除此行内容。

## 调用信任边界

`isUnsafeContext = true` 表示来自 Controller、RPC、消息等外部或不可信入口。此时请求对象必须执行越权、越范围和危险操作校验。

`isUnsafeContext = false` 表示内部可信调用；权限责任由内部调用方承担，请求对象不重复施加外部入口校验。

外部请求不能自行把该值设置为 `false`。

## 跨请求对象上下文

基础请求对象会把当前请求整体导出为 DAO 本地上下文变量 `_req`：

```java
@CtxVar(varName = "_req")
public <T extends BaseReq> T getRequestContext() {
    return (T) this;
}
```

它用于同一个 DAO 构建过程中的后续查询、选择、统计或更新对象跨类读取原始请求信息。请求对象自身的
SpEL 直接调用自身方法即可，无需通过 `_req`。

例如，先追加查询请求，再追加统计对象时，统计对象可以写：

```java
@Where(condition = "#_req.isCanVisitPersonalData()")
boolean includePrivateData;

@Select(condition = "#_req.isTenantUser()")
String tenantOnlyColumn;
```

也可以在参数表达式中取具体值：

```java
@Eq(value = "ownerId", paramExpr = "#_req.get_currentUserId()")
boolean onlyCurrentUser;
```

`_req` 本身是整个对象，不应直接作为 SQL 参数；应从中读取标量或集合属性。普通结果 DTO 若没有作为
DAO 构建对象被处理，不会自动获得该上下文。

## 租户范围

租户用户（含租户管理员）的 `tenantId` 必须由服务端上下文提供，并且必须等于当前用户租户 ID。
注入阶段负责覆盖、必填校验；DAO 构建条件时再次校验，缺失、空白或不匹配均抛异常，内部调用也不能跳过。
身份标志和当前用户租户 ID 必须来自可信上下文，不能由客户端赋值。

请求对象默认按租户用户处理，`isTenantUser` 上下文缺失时也为 true。
平台身份需要显式满足 `isPlatformUser=true` 且 `isTenantUser=false`；超级管理员身份也要求有效平台身份。

按三类用户和两类操作划分：**超管类**包含超级管理员、平台管理员；**租户用户**包含租户管理员。
表中的额外公共/共享数据均须对应能力接口和请求开关同时允许。

| 用户类别与租户视角 | 查询 | 更新、删除 |
| --- | --- | --- |
| 超管类，未指定租户 | 不追加任何租户条件 | 不追加任何租户条件 |
| 超管类，指定租户 | 指定租户 OR 平台数据，可额外加入共享数据 | 与查询相同，可额外加入共享数据 |
| 普通平台用户，未指定租户 | 仅 `tenantId IS NULL`，不追加共享条件 | 仅 `tenantId IS NULL` |
| 普通平台用户，指定租户 | 指定租户，可额外加入公共/共享数据 | 拒绝，不能写入租户数据 |
| 租户用户，自身租户 | 自身租户，可额外加入公共/共享数据 | 仅精确匹配自身租户 |

普通用户的公共查询扩展需要 `MultiTenantPublicObject` 和 `isContainsPublicData()` 同时允许；共享扩展需要
`MultiTenantSharedObject` 和 `isTenantShared()` 同时允许，并且必须指定目标租户。
额外条件与基础租户范围取 OR，再与主键、乐观锁及其他条件取 AND。普通用户的共享标志不能扩大更新、删除范围。
“平台数据”指租户 ID 为空的数据；管理员操作它的权限不依赖公共查询开关。
普通用户查询可按明确的公共/共享声明读取范围内数据，但这不授予跨租户修改权限。

`@Eq` 保持默认的非空条件；空租户不会由它自动生成 `IS NULL`。平台数据条件由单独的 `@IsNull` 控制。
平台管理员字段和方法统一为 `isPlatformAdmin` / `isPlatformAdmin()`，不保留旧命名的兼容 API。
注入上下文统一使用 `InjectConst.IS_PLATFORM_ADMIN`（键为 `isPlatformAdmin`），不再读取旧的平台管理员上下文键。

### 为什么这样划分

- **租户隔离优先于角色便利性**：租户管理员也只管理本租户。请求租户缺失或与登录租户不同必须拒绝，
  不能通过省略 WHERE 条件“容错”，否则会放开其他租户的数据。注入与条件构建分别校验，保护正常入口与直接构造请求的调用。
- **普通用户可读不等于可写**：公共数据供多个租户复用，共享数据可属于其他租户。公共/共享查询开关只扩大其读取范围，
  不授予租户用户更新或删除数据提供者记录的权限。
- **平台身份不等于平台管理权限**：普通平台用户默认只操作无租户归属的平台数据；指定租户可切换查询视角，
  不能因此获得写该租户的权限。无目标租户时也不应把所有租户共享记录拉进平台视角。
- **管理员需要可控的跨租户管理范围**：超级管理员和平台管理员无目标租户时使用全局视角；指定目标后，
  基础范围统一为“指定租户 OR 平台数据”，让读、改、删对同一管理视角保持一致。
  超管类原本有权修改任意租户记录；指定租户、公共/共享选择是主动收窄范围以减少误操作，不是授予新权限。
  因此指定租户且具备共享能力、请求开启共享时，查询、更新、删除均加入 `OR tenantShared = true`。
  例如选择租户 A 并开启共享，可操作 A、平台数据和其他租户的共享记录，但不匹配其他租户的非共享记录。
- **范围并集不能绕过记录定位**：租户范围的 OR 必须成组，再与主键、版本等条件取 AND。
  管理员无租户条件并不表示无需主键、乐观锁、组织或个人权限等其他约束。

## 组织范围

`orgIdList` 是注入提供方已经校验过的组织访问范围。请求对象只消费该范围，不重复校验列表中的组织成员权限。

- 拥有全部组织权限且没有指定组织范围：不附加组织条件。
- `orgIdList` 非空：生成 `org_id IN (...)`，用于查询、更新和删除的旧记录范围。
- 列表为空、`orgId` 非空：查询、删除及非管理员更新时按单个组织筛选；管理员更新时 `orgId` 是新的组织归属。
- 不安全上下文下，无全部组织权限且没有任何组织范围：抛异常。

| 操作与身份 | `orgIdList` | `orgId` |
| --- | --- | --- |
| 查询，任意身份 | 有效列表优先作为 WHERE 条件 | 列表为空时作为 WHERE 条件 |
| 删除，任意身份 | 有效列表优先作为 WHERE 条件 | 列表为空时作为 WHERE 条件，删除不存在 SET |
| 更新，非管理员 | 有效列表优先作为 WHERE 条件 | 列表为空时作为 WHERE 条件，不能修改组织归属 |
| 更新，管理员 | 作为旧记录的 WHERE 组织范围 | 作为新组织归属写入 SET，不能替代旧记录范围 |

没有全部组织权限的外部管理员更新时，必须提供有效的 `orgIdList`；只有新 `orgId` 不足以授权旧记录操作。
全部组织权限允许不限定旧组织范围，但不自动赋予变更归属权限，SET 仍要求 `isAdmin()`。
列表包含 null 或空白组织 ID 时拒绝，避免参数过滤后组织条件消失。
这样既能让非管理员通过单个组织缩小修改范围，也能防止管理员把“转入哪个组织”误当作“可以操作哪些旧记录”。

## 个人范围

个人数据访问授权由上游权限系统决定，通过可信上下文键 `isCanVisitPersonalData` 注入。
请求对象的 `isCanVisitPersonalData()` 只返回注入的布尔字段，不再根据 TOP 超管身份或保密等级计算权限。
所有身份均须由上下文明确授权；未提供时为 false，并覆盖客户端伪造或复用请求残留的 true。
该值为 false 不影响在合法租户、组织范围内操作自己的记录，也不影响独立的敏感级别过滤。

### 拥有者注入与顺序

模板中的 SpEL 表达式常量统一使用 `EXPR_` 前缀，例如 `EXPR_IS_UNSAFE_CONTEXT`。
`InjectConst.IS_UNSAFE_CONTEXT` 等仍是原始上下文键常量，名称和值保持不变。

`MultiTenantPersonalReq` 和 `MultiTenantOrgPersonalReq` 的 `ownerId`、`ownerIdList` 都使用 default 域
`@InjectVar`，读取可信上下文的同名键。`isOverride` 和 `isRequired` 均使用 `EXPR_NOT_IS_CAN_VISIT_PERSONAL_DATA`：

| 可信上下文个人访问授权 | 覆盖已有拥有者值 | 上下文值是否必需 |
| --- | --- | --- |
| false 或缺失，不区分管理员身份 | 是；用于筛选旧记录的范围必须是本人 | 两个值均必需，不能靠请求传入值代替 |
| true，不区分管理员身份 | 否；保留显式值，未填时允许上下文补值 | 否 |

该表达式使用 `#isCanVisitPersonalData`，直接读取解析器的授权上下文，不调用请求对象的权限方法。
正确流程是上游先完成授权计算，再注入 DTO；权限字段和拥有者字段读取同一份上下文，不依赖字段注入顺序。
不得把尚未注入的 DTO 字段或客户端提供的权限作为上下文来源。

以上只决定注入与覆盖，实际操作仍须满足旧记录拥有者范围、租户与组织边界。

| 场景 | 规则 |
| --- | --- |
| 具有个人访问权限 | `ownerIdList`、`ownerId` 可填可不填；查询、删除及非管理员更新按列表优先筛选；管理员更新的单个 `ownerId` 是 SET 新值，见下表。 |
| 无个人访问权限 | 不安全上下文下，列表有效时只能包含本人；否则用于筛选的单个 `ownerId` 必须等于本人。当前用户 ID 缺失也拒绝。 |
| 修改 `ownerId` | 仅管理员可以修改个人数据归属。 |
| 删除个人数据 | 按上下文授权处理：有个人访问授权可在父级范围内删除指定拥有者记录，否则仅本人；不再额外要求管理员身份。 |

| 操作与身份 | `ownerIdList` | `ownerId` |
| --- | --- | --- |
| 查询、删除，任意身份 | 列表优先用于 WHERE | 列表为空时用于 WHERE |
| 更新，非管理员 | 列表优先用于 WHERE | 列表为空时用于 WHERE，不能修改归属 |
| 更新，管理员 | 限定旧记录的 WHERE 范围 | 仅用于 SET 新归属 |

无个人访问授权的外部管理员更新时，必须提供仅包含本人的旧拥有者列表；新的 `ownerId` 不能代替旧范围。
新拥有者合法性应由上游授权确认。拥有个人访问授权的管理员可不指定旧拥有者列表，仍受主键、租户和组织条件限制。
列表含 null/空白成员时拒绝，避免 IN 过滤后意外丢失范围；列表有效时不再用被覆盖的单值校验旧记录范围。

### 拥有者条件入口

两个个人请求模板统一使用以下双参数入口：

```java
ownerIdListCondition(boolean isQueryAction, boolean isDeleteAction)
ownerIdCondition(boolean isQueryAction, boolean isDeleteAction)
```

生成注解由 DAO 提供操作标志：

```java
@In(value = "ownerId", condition = "ownerIdListCondition(#_isQuery, #_isDelete)")
@Eq(condition = "ownerIdCondition(#_isQuery, #_isDelete)")
```

上面两条注解分别位于 `ownerIdList` 和 `ownerId` 字段上，不应同时放在同一个字段。

| 操作 | `isQueryAction` | `isDeleteAction` |
| --- | --- | --- |
| 查询 | true | false |
| 更新 | false | false |
| 删除 | false | true |

单参数 `ownerIdListCondition(boolean isDeleteAction)` 已删除，不再保留兼容入口。
原有直接调用应迁移至双参数版本。不能用 `!isDeleteAction` 代替 `isQueryAction`，否则会把更新误判成查询，
混淆管理员的 SET 新归属与旧记录 WHERE 范围。一般业务代码只需使用生成的请求对象，让 DAO 传入操作标志。

个人条件叠加在租户和组织条件之后：

```text
MultiTenantPersonalReq
  = 租户范围 AND 个人拥有者范围

MultiTenantOrgPersonalReq
  = 租户范围 AND 组织范围 AND 个人拥有者范围
```
