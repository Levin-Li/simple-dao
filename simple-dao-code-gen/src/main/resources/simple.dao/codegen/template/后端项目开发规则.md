本文件是 `backend` 范围内当前仓库的项目级裁决规则。

如果本文件与《模块开发说明》、 《代码生成说明》或其他通用模板/流程说明发生冲突,以本文件为准。

需要新增第3方组件库时,务必生成对应的变更记录.
这个项目的Dao层采用simple-dao (https://github.com/Levin-Li/simple-dao 4.3.0 分支)框架, 一般情况下不直接编写查询语句,一般直接通过DTO对象的字段上添加注解来实现查询和修改的功能,具体请参考simple-dao的文档, 和当前项目中的的使用方式.
后端查询、详情、修改、删除、状态变更等逻辑,默认遵守“查询对象 + DAO/simple-dao”原则,不直接手写查询语句,除非规则文件明确允许.
关于JDK, 请根据项目的根pom中对Java版本的要求, 自行选择JDK, JDK优先从已经安装的JDK中查找.
建议项目统一使用 JDK 25（如 Corretto 25）进行编译、测试和代码生成；不要使用 JDK 26 或其他更高版本替代.

涉及前端页面、浏览器页面、交互流程、视觉状态、下载行为、路由可访问性或用户当前页面问题的验证,必须统一使用用户当前的 in-app browser 进行验证. 不得用独立 Playwright 浏览器、系统浏览器或其它隔离浏览器的结果替代当前 in-app browser 的验证结论. 只有在用户明确要求隔离浏览器测试,或当前 in-app browser 工具不可用且已说明原因时,才允许使用其它浏览器工具作为补充;补充结果必须明确标注不能代表用户当前浏览器现场.

修改代码,或是新增类文件时,需要符合项目的代码规范.
项目的编码规范,采用阿里云Java编码规范.类的字段之间要换行.
对于POJO,VO,BO,DTO的类定义要求使用@Data @Accessors(chain = true)注解, 类的字段之间要换行.
后端实体字段如果是枚举类型,数据库中必须存储枚举常量名,不得存储枚举的编号、ordinal或code值;JPA实体字段应使用@Enumerated(EnumType.STRING)声明.

第三方接口对接规则:
- 对接第三方HTTP API时,请求参数、响应结果应尽量定义为明确的DTO/模型类,并抽象公共请求、响应结构,避免在业务代码中直接通过JSONObject、Map或字符串字段名读取数据.
- 对接第三方接口前,请求所使用的工具类或请求封装方式,如果项目中没有明确既有约定,必须先跟项目负责人确认后再实现.
- JSON解析统一优先使用Fastjson2. 对于第三方接口中常见的下划线命名、大小写不稳定、驼峰/蛇形混用等字段,优先使用`JSONReader.Feature.SupportSmartMatch`进行智能匹配;只有字段冲突、语义不一致或智能匹配无法稳定解析时,才使用`@JSONField`等显式注解.
- 第三方接口的异常响应、HTML响应、纯文本响应或非标准JSON,应在接口适配层统一转换成清晰的内部异常信息,不应直接透传原始响应给前端.

项目的服务类分为两种:业务服务类和默认服务类. 业务服务类是为了满足业务需求而定义的服务类,类名必须以`Biz`为前缀,以`Service`结尾;默认服务类是CRUD操作相关的服务类,是通过'simple-dao-codegen'插件生成的服务类,类名以实体类的简单类名为前缀,以`Service`结尾,默认服务类不允许手动修改,如果需要新增业务相关的服务方法,请在业务服务类中新增方法.

业务服务实现优先级规则:
- `Biz`开头的业务服务在实现业务能力时,必须优先复用已有的默认CRUD服务、生成查询/更新请求对象以及现成服务方法,不要一开始就绕过基础能力单独下沉实现.
- 当默认CRUD服务无法直接满足需求时,第二优先级是通过自定义DTO/BO/Req并结合simple-dao注解扩展能力来实现;应优先参考现有业务服务实现类中的`stat`方法写法,通过查询对象、统计对象和注解表达筛选、聚合、分组、排序以及数据范围约束.
- 只有在“默认CRUD服务 + 自定义DTO/BO/Req + 注解扩展”仍然无法满足需求时,才允许做DAO扩展;DAO扩展是最后手段,不得作为`Biz`业务服务的默认实现路径.
- `Biz`业务服务中如果最终使用DAO扩展,实现前应先明确说明前两层方案为什么不能满足,避免重复引入本可由基础CRUD或注解模型解决的复杂实现.

项目的控制器类也分为业务控制器类和默认控制器类. 业务控制器类是为了满足业务需求而定义的控制器类,类名必须以`Biz`为前缀,以`Controller`结尾;默认控制器类是CRUD操作相关的控制器类,是通过'simple-dao-codegen'插件生成的控制器类,类名以实体类的简单类名为前缀,以`Controller`结尾,默认控制器类不允许手动修改,如果需要新增控制器方法,请在业务控制器类中新增方法.

所有新增的服务类,都必须分为接口和实现类,它们的包名必须相同, 接口类名必须以`Biz`为前缀,以`Service`结尾. 实现类名以`Biz`为前缀,必须以`ServiceImpl`结尾, 接口类必须定义在`services`模块的biz目录中, 实现类必须定义在`services-impl`模块的biz目录中.实现类的相关注解定义必须参考多个已有的实现类.

业务控制器请求对象与数据安全规则:
- 业务控制器方法不得直接使用零散参数承载可持久化业务数据的查询、详情、修改、删除、状态变更等入参,尤其不得直接使用裸`id`访问业务数据. 业务接口入参应以请求对象为主,通过请求对象承载租户、组织、个人等数据归属上下文,方便统一注入、过滤、鉴权和扩展.
- 业务控制器方法在非特殊情况下应尽量避免使用路径变量承载入参,尤其不应使用ID作为路径变量访问可持久化业务数据. 涉及业务数据访问、修改、删除、状态变更的ID条件,应放入请求对象中,避免绕过租户、组织、个人等数据范围约束.
- 这样做的主要目的是数据安全:如果接口只接收裸`id`,而没有同时绑定租户、组织或个人访问范围,访问者可能通过猜测或获取其它租户的数据ID越权读取或操作数据.
- 请求对象的选择应以实体对象的数据归属能力为基准. 如果实体是`MultiTenantObject`,相关业务请求对象必须继承`MultiTenantReq`,或复用该实体已有的多租户请求对象. 如果实体同时是`MultiTenantObject`和`OrganizedObject`,相关业务请求对象必须继承`MultiTenantOrgReq`,或复用该实体已有的多租户组织请求对象. 如果实体同时是`MultiTenantObject`、`OrganizedObject`、`PersonalObject`,相关业务请求对象必须继承`MultiTenantOrgPersonalReq`,或复用该实体已有的多租户组织个人请求对象. 如果实体只涉及多租户和个人归属,不涉及组织归属,应使用或继承对应的多租户个人请求对象.
- 查询类接口如果已有可复用的查询请求对象,应优先复用或继承已有查询对象. 多数情况下,通过继承原有查询对象并补充少量业务字段,就可以复用已有的租户、组织、个人过滤能力以及通用查询条件,避免重新定义散参数.
- 如果查询条件非常固定、明确,并且确实不需要原查询对象中的其它查询参数,可以定义更小的专用请求对象;但该请求对象仍必须按对应实体的数据归属能力继承对应安全基类,不能退化为裸参数或无数据范围约束的普通对象.
- ID类接口如果只需要ID和数据访问范围,应直接复用对应实体的`XxxIdReq`,不要使用单独的`id`、`tenantId`、`orgId`等散参数. 如果业务接口以ID为基础定位条件,但还需要扩展其它业务参数,应优先继承对应实体的`XxxIdReq`后再补充扩展字段,不要重新定义无数据范围约束的ID字段.
- 业务对象DTO、BO、请求对象等非生成的业务入参类,必须放在`services`模块的`.biz.bo`包路径下;必要时按业务域建立子包. 控制器模块不得临时定义业务DTO.
- 默认CRUD控制器、默认服务、生成请求对象的处理方式应优先参考基础控制器和代码生成器已有定义;新增业务控制器方法也应尽量复用这些已有请求对象和过滤能力.
- 明确不归属租户、组织、个人的数据对象,可以使用普通请求对象或`BaseReq`. 无持久化数据访问、无数据归属风险的工具型接口,可以使用简单参数. 任何涉及业务数据读取、修改、删除、状态变更的接口,不应使用裸ID或散参数绕过请求对象.
- 业务服务层在根据ID加载数据时,应尽量通过对应的`XxxIdReq`或查询请求对象执行查询,而不是先按裸ID查出实体后再手动判断租户、组织或个人权限. 数据范围过滤应尽量前置到查询条件中,减少越权数据被加载到内存的机会.

如果一个目录中有名称为'code-gen.md'的文件, 则表示该目录下的文件是通过代码生成器生成的, 请不要修改任何文件,并且不能在该目录和其子目录中新增任何文件.
如果一个目录中有名称为'模块开发规则.md'的文件, 则表示该目录下的开发要遵循这个规则.

有涉及到实体类的开发,请按照以下顺序和规范进行开发: 先添加实体类, 添加实体类时请参考'实体类开发规范.md';实体类添加后,先单独清除实体模块原有的编译结果,然后再单独编译实体类模块,并确保编译通过.编译通过后,请务必进入到实体类模块的目录中执行'simple-dao-codegen'插件的'gen-code'任务,并确保任务执行成功. 任务执行成功后,会生成对应的服务类和控制器类,请根据这个确认任务是否执行成功;在服务类和控制器类中,请根据需要添加对应的方法,并确保方法的参数和返回值符合项目的代码规范.实体类对应的默认服务类,必须通过simple-dao-codegen插件生成.请不要手动编写默认服务类.实体类对应的默认控制器类,必须通过simple-dao-codegen插件生成.请不要手动编写默认控制器类.

当实体类发生变更时,请进入到实体类模块的目录中重新执行'simple-dao-codegen'插件的'gen-code'任务,并确保任务执行成功.

对于业务服务类中的方法,请编写对应的测试用例,尽量覆盖所有的业务场景.

异常的抛出, 尽量通过Hutool的断言工具类(Assert)来抛出.

服务类和控制器类都需要用Swagger的@Operation注解来描述方法的功能和返回值要求.

在支持链式调用的情况下, 尽量使用链式调用.

开发环境下请使用'dev'环境, 测试环境请使用'test'环境, 生产环境请使用'prod'环境.

进入根模块的目录中执行'simple-dao-codegen'插件的'copy-template'任务, 会在项目根目录下生成docker-compose目录, 里面有 PG 数据库和Redis, 可用于开发环境.

开发环境下启动PG数据库,请执行docker-compose目录下,有一个postgresql相关的目录, 请进入该目录, 执行startup.sh 启动PG数据库.
开发环境下启动Redis,请执行docker-compose目录下,有一个redis相关的目录, 请进入该目录, 执行startup.sh 启动Redis.

开发和页面联调需要测试数据时,开发代理应自行准备测试数据,可以通过已有服务、接口、初始化脚本或直接连接开发数据库写入数据. 不得要求用户手工造数,也不得因缺少数据跳过接口或界面验证.

直接写数据库仅允许用于本地或开发环境验证,不得面向测试、预发、生产环境执行. 写入的数据应使用清晰可识别的编码、名称或备注,并尽量保持可重复执行、可清理;涉及枚举字段时仍必须写入枚举常量名,不得写入 ordinal 或 code 值.

项目主要基于spring boot , 所有的构件都要检查是否支持和兼容spring boot的版本, 这样可以减少很多运行时错误.
